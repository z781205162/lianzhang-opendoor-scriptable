# 技术实现说明

> 免责声明：本文仅供合法授权范围内的学习、研究和个人设备自动化使用。它不构成绕过门禁认证或访问他人设备、账号、场所的授权。请遵守所在地法律法规及门禁管理规则，并自行承担使用责任。

## 1. 目标

将联掌门户移动端的一次开门请求整理为 Scriptable 脚本：运行脚本时生成短时有效的时间戳和签名，读取本机 Keychain 中的认证配置，向开门接口发送 POST 请求，并根据返回码显示成功或失败提示。

## 2. 数据来源与抓包流程

只对已授权账号和同一扇门操作：

1. 在 Mac 上发现当前局域网 IP 和 mitmproxy 实际监听端口，不使用历史端口。
2. 让 iPhone 临时使用该代理，并完成证书信任。
3. 退出并重新登录联掌门户。
4. 对同一扇门连续开门三次。
5. 保存 flow 到本地，仅用于字段核对；完成后删除 flow，并关闭 iPhone 的代理。

抓包文件属于高敏感材料，不能进入 Git 仓库、云盘或聊天记录。

## 3. 请求组成

根据已授权设备上的请求样本，通常需要整理出：

- 登录响应中的 `openid` 和 `token`；
- 开门请求中的门禁序列号（示例中记作 `SERIAL_PLACEHOLDER`）；
- 移动端请求头对象；
- 与设备版本匹配的 User-Agent；
- 开门接口的路径和服务端地址。

这些字段只应保存在本机 Keychain 或其他受保护的本地存储中。

## 4. 动态签名

脚本每次运行时生成 Unix 秒级时间戳 `timestamp`，并使用服务端约定的拼接规则计算签名：

```text
sign = MD5(API_PATH + timestamp + token)
```

其中 `API_PATH` 是开门接口路径，`token` 从本机 Keychain 读取。时间戳、签名和 openid 作为查询参数或请求字段发送，具体位置以当前设备抓取并核验的请求为准。

不要把签名提前写死：签名依赖当前时间戳和认证材料，旧签名通常会过期。

## 5. Scriptable 执行流程

```text
读取 Keychain 配置
  -> 校验必要字段存在
  -> 生成 timestamp / msg_id
  -> 计算动态 sign
  -> 组装查询参数、请求头和 JSON body
  -> POST 到开门接口
  -> 检查响应 code
       -> 成功：通知 + 短暂成功提示
       -> 失败：显示服务端 code/message
```

配置初始化脚本只负责把用户自己的认证材料写入 Keychain；一键开门脚本不应把 token 或 openid 写在源码中。

## 6. 三次请求核验

生成个人配置前，应核对同一接口最近三次请求：

- 三次响应均为服务端成功状态；
- 三次请求属于同一扇门；
- `timestamp` 均为请求当时生成的值；
- 签名按服务端规则重新计算后能够匹配；
- 没有把另一台设备或另一扇门的字段混入配置。

## 7. 故障排查

- `401/未授权`：重新登录并更新本机 Keychain 配置，不要把新 token 发到聊天或提交到仓库。
- 签名错误：检查接口路径、时间戳单位、拼接顺序和 token 是否来自同一账号。
- 门禁不匹配：重新核对 `SERIAL_PLACEHOLDER` 与实际开门请求。
- TLS/证书错误：关闭代理后再运行；不要通过关闭证书校验来绕过问题。
- 脚本无提示：分别测试 Scriptable 前台运行、通知权限和小组件运行环境。

## 8. 风险边界

该方案复现的是已授权移动端请求，不绕过账号登录、门禁授权或服务端权限。任何超出本人授权范围的测试都应停止。
